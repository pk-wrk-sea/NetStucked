# Network behavior

## Current Port Test (0.4.1)

Port Test continuously scans the authorized Host/IP/CIDR × selected ports after Start; Pause and Stop await cancellation. Inclusive ranges such as `1000-1005` expand to six ports and deduplicate with other entries. Limits remain 1,024 hosts, 64 unique ports and 16,384 checks, with acknowledgement above 4,096 checks, 32 concurrent probes and 128 send admissions/second.

Packet Size specifies 0–1400 zero-filled payload bytes, default 32, for TCP and UDP. TCP measures actual connect duration, sends all requested bytes under the same timeout and handles partial sends. Send completion does not prove a service-level response; failure after connection has explicit payload-send details. Size zero tests only TCP connection or sends an empty UDP datagram. UDP response time is measured only after a real received datagram; No response remains inconclusive. Actual sent-byte counts are included in details/CSV. Operating-system TCP segmentation and protocol headers are outside this payload-size setting.

TCP Port Test behavior added in 0.2.0 is specified in [FEATURES_0.2.0.md](FEATURES_0.2.0.md): actual cancellable TCP handshakes, DNS isolation, per-endpoint ownership, successful connect times only, independent outcome/history counters and bounded rate/concurrency. The ICMP behavior below remains in use.

Only explicitly selected, authorized targets are probed using cancellable .NET ICMP APIs. No shell ping/tracert process or production test adapter is used. ICMP response/loss describes ICMP traffic; it does not establish all-service availability.

IPv4 CIDR masks the input first, excludes network/broadcast through /30, includes both /31 addresses and one /32 address. Malformed IPv4/hostname, IPv6 CIDR, oversized scopes and invalid lines are rejected before starting. Input is bounded to 1 MB / 10,000 lines. Deduplicate without case; first occurrence wins description. The desktop fixes the expansion cap at 1024 instead of exposing a larger-scope setting.

Desktop Live Ping defaults: 1000 ms start-to-start interval, 2000 ms timeout, 32-byte payload. Internal desktop limits are 64 workers and 2048 ICMP sends/second, token-bucket burst at most eight. The UI exposes only interval (250–60000 ms), timeout (500–10000 ms), and payload (1–1400 bytes). Each target has one outstanding work item and cannot overlap itself. Initial deadlines are staggered; a monotonic scheduler skips missed deadlines under capacity/timeout pressure. The requested interval is best effort. Fast targets do not await a whole target batch. DNS uses separate bounded workers within the same concurrency cap; literal IPs bypass DNS. Resolution caches for 30 seconds, failures retry after five seconds, actual DNS calls time out after three seconds. Auto prefers IPv4; literal IPv6 Ping uses the real API.

Only completed requests increment Sent, Received or Lost. DNS errors are Unknown and add no ICMP loss. Pause stops admission, cancels active calls and waits for a quiescent boundary. Resume retains real samples; Stop awaits every worker before reuse. Sent = Received + Lost. Last is absent for a failed outcome; average/min/max use successful replies. Three consecutive failed completed attempts make the aggregate status Unreachable; earlier failures or RTT/loss warning thresholds produce Warn. Histories show each individual actual outcome as Up or Unreachable, rather than the aggregate warning state. Histories are bounded to 500 per target and 100,000 overall.

Last ping and Last success are times of completed requests, never scheduled attempts. Reachable since and Unreachable since mark the beginning of the current completed reply/no-reply streak, with the opposite field cleared on transition. DNS failures and cancellation do not invent a timestamp or transition. Result / error is the actual responder or returned API/DNS failure. Since fields therefore describe completed ICMP evidence, independently of the aggregate three-failure warning threshold.

Desktop Traceroute uses IPv4 ICMP only: Max hops 30, interval 1000 ms, timeout 1500 ms, payload 32 bytes. Settings expose Max hops (1–64), per-hop interval (250–300000 ms), timeout (500–10000 ms) and payload (1–1400). Continuous polling is forced on; one sample per hop/interval. Initial discovery uses a rolling window of at most four distinct TTLs, admitting the next TTL as soon as a slot completes. Verified destination replies publish immediately; speculative higher TTLs are cancelled and awaited. Terminal ICMP errors stop progression; unanswered hops continue through Max hops. The Core API retains one-shot/refinement support for tests and other callers, while desktop sessions use continuous independent polling.

Once the path is discovered, each known TTL owns its own monotonic polling loop, with staggered deadlines and up to 32 simultaneous distinct TTLs per session. A slow hop does not hold a fast hop's next poll. No same-TTL request overlaps itself; capacity/slow requests skip expired intervals. Rediscovery occurs every 30 seconds, after observed alternate responders, after three missing destination replies, or when the destination responds at a shorter TTL. Generation cleanup is awaited before rediscovery. A logical comparison round completes once all known hops have new completed evidence; faster hops can produce extra samples while others wait. Missing responses preserve responding baselines. Paused/cancelled partial rounds do not commit route changes.

Each trace session owns its own engine, statistics, event log and cancellation; a paused/closed session leaves the others running. The desktop caps sessions at eight. The shared real ICMP adapter limits outstanding native Ping calls to 128 across the application. RTT measurement starts after this shared admission queue. Core tests use deterministic adapters; they never substitute for production APIs.

TtlExpired/TtlReassemblyTimeExceeded identify responders; Success from the resolved destination establishes the path end. Missing replies have no RTT and report No final reply rather than host offline. Echo RTT uses PingReply.RoundtripTime. Responding TTL/terminal ICMP errors use Stopwatch around the completed API call because Windows may return an unreliable zero RoundtripTime for these replies. This includes API overhead, excludes the application admission queue and is not a fabricated network measurement. Reply TTL is displayed only if provided by the API.

Per-hop jitter is the mean absolute delta of successive valid responding RTTs. Compare responding address sets at the same TTL only with completed-round evidence. Newly observed alternatives create Route events; ECMP may account for differences. The event log records lifecycle, destination outcome transitions, route observations and actual errors. Identical repeated errors/outcome/route messages are suppressed for ten seconds, with bounded deduplication state. Normal probe replies and completed rounds create no events. Retain at most 1000 events/64 hops. Optional Core reverse DNS remains independent and cached; it is off in the simplified desktop defaults.

The visible page applies revision deltas every 33 ms with a cooperative 4 ms budget. Only changed cell properties notify WPF. Sort/filter refresh is needed only when its actual keys/membership change, throttled to 500 ms while running and deferred during description editing. Main-page views are retained across navigation, with inactive presentation timers stopped. A cheap activity timer reads engine state without requesting snapshots. Engine timing and skipped/cancelled work remain separate from ICMP RTT/loss. No automatic updater is present.
